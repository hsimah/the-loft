## Fix first

### 1. Health checks can report unreachable endpoints as healthy

**Confirmed code defect, obscured by the documentation.** [common.sh](../../control-plane/common.sh), lines 90–92, captures curl's HTTP code and appends `000` on failure. A connection failure already prints `000`, producing `000000`, which does not equal the failure sentinel. An isolated test of the actual `check_url` function with a mock failing curl printed:

```text
local  OK  http://unreachable.invalid — HTTP 000000
exit=0
```

[common-sh.md](../scripts/common-sh.md), lines 72–85, and [DEBUG.md](../../DEBUG.md), lines 64–80, promise that no response fails. That promise is false. The checker also uses `curl -k`, so the `ssl` tier does not validate certificate trust, and accepts HTTP 500/502 as success. `check_containers` inspects the containers returned by `compose ps`, without comparing them with the expected service set or checking Docker health status.

**Action:** fix the curl exit-status handling separately from this documentation cleanup. Describe the current checks as limited reachability/state checks; do not present them as TLS, application, or VPN validation. Merely changing the URL to `/health`, as common-sh.md suggests, does not fix acceptance of error status codes.

### 2. Caddy's documented host admin endpoint does not exist in Compose

[mushr.md](../services/mushr.md), line 56, claims the container's loopback admin listener is reachable through a host port binding. [Caddyfile](../../services/mushr/Caddyfile), line 2, listens on `127.0.0.1:8880` inside the container; [Compose](../../services/mushr/docker-compose.yml) publishes only 80 and 443. The configured `[mushr:local]` host health URL is therefore inconsistent too.

**Action:** use an in-container admin probe, for example `sudo docker exec mushr wget -qO- http://127.0.0.1:8880/config/`. Correct the host health check implementation; do not add public admin exposure just to match the notes. Remove host `curl localhost:8880` recipes from DEBUG.md and mushr.md. Container-local health checking already uses the appropriate endpoint.

### 3. The proposed Gmail scope is not draft-only

[sputnik.md](../services/sputnik.md), line 143, recommends `gmail.compose` with the claim that a human must still press send. That scope permits both managing drafts and sending mail. [Google's scope reference](https://developers.google.com/workspace/gmail/api/auth/scopes) explicitly grants both.

**Action:** remove the draft-only claim. Keep the current read-only workflow; any future draft-writing feature needs a separate design for approval before sending. This finding concerns the proposed change, not evidence that current credentials have this scope.

### 4. The universal container-ownership rule is false

[README.md](../../README.md), line 108, says all containers run as UID/GID 1003. The manifests do not enforce that: n8n explicitly uses 1003, slskd uses variables, Plex maps `PLEX_UID`, and many images keep their own defaults. [pupyrus.md](../services/pupyrus.md) itself documents WordPress files as UID 33 while another paragraph says both data directories belong to littledog. [pawpcorn/.env.example](../../services/pawpcorn/.env.example) specifies PUID 1004, whereas setup creates new littledog accounts as 1003 and preserves existing accounts.

The generic `chown -R littledog:pack-member` recovery instructions in [DEBUG.md](../../DEBUG.md), lines 462–477, 687–703, and 1072, can conflict with the service's actual runtime user. Host account group membership also does not by itself establish the groups of an in-container process; Plex/audio explanations blur those two concepts.

**Action:** replace the blanket claim with service-specific ownership requirements. Treat existing host UIDs and effective container users/groups as live checks, not inferred facts. Keep provisioning directory ownership distinct from application data ownership.

### 5. Database recovery instructions overstate what is safe

[DEBUG.md](../../DEBUG.md), lines 812–854 and 1076–1088, labels `MARIADB_AUTO_UPGRADE=1` as recovery for InnoDB corruption. Upgrade handling and corruption recovery are different operations; MariaDB documents [InnoDB recovery modes](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-troubleshooting/innodb-recovery-modes) separately.

Three documents also infer that `tc.log` is always safe to delete because WordPress does not use XA. MariaDB has [internal XA coordination](https://mariadb.com/docs/server/reference/sql-statements/transactions/xa-transactions), so the application's lack of explicit XA transactions is insufficient evidence. The older pupyrus/space-needle pages blame setup recreation; DEBUG.md records a later shutdown-timeout diagnosis, and [daemon.json](../../daemon.json) now contains `shutdown-timeout: 90`.

**Action:** keep one database incident record with its date, observed error, applied mitigation, and limits. Replace universal deletion/auto-upgrade recipes with a backup-first, error-specific recovery runbook. Do not silently choose one historical diagnosis as proven for every recurrence.

### 6. Hardlink and download-cleanup guarantees are unsupported

[stellarr.md](../services/stellarr.md), lines 34–59, and [pawpcorn.md](../services/pawpcorn.md), line 31, promise hardlinks and zero extra disk usage. The *arr [Compose definitions](../../services/stellarr/docker-compose.yml) mount `/downloads` and `/movies`, `/tv`, or `/music` separately. Servarr's [Docker guide](https://github.com/Servarr/Wiki/blob/master/docker-guide.md) explains why separate container mounts prevent this hardlink layout even when the host paths share a filesystem.

The [cleanup script](../../services/stellarr/transmission/remove-torrents.sh) checks ratio only, then removes torrents and data. It never verifies that an import completed. Copies may preserve successfully imported media, but neither successful import nor hardlinking is established by this script.

**Action:** remove the unconditional safety claim. Verify existing imports and inode/link counts on the host before planning a mount-layout or cleanup change. Correct the accompanying slskd path description too: configured downloads go under `/mammoth/downloads/complete/lidarr`, not the `/mammoth/downloads/soulseek` tree described elsewhere.

### 7. The July upgrade plan is historical and includes a fleet-wide stop

[fleet-upgrade-2026-07.md](../../plans/fleet-upgrade-2026-07.md) still targets MA 2.9.9 and NordVPN `v3.12.3`. Current Compose uses MA 2.10.1 and a VPN digest explicitly documented as replacing the nonworking tag. Its howlr backup recipe, line 160, stops the entire Docker daemon, suppresses failure, and supplies no explicit restart step, despite promising service-at-a-time changes. Its follow-up about the old DEBUG.md howlr container table has already been addressed.

**Action:** archive the plan as a dated migration record. Extract still-open maintenance work and service-specific backup/verification steps. Do not offer the old commands as today's upgrade procedure.

### 8. Pinning is not a complete rollback guarantee

[README.md](../../README.md), lines 32–46, says `git revert` provides rollback and the old image remains available locally. Data migrations can make old images unusable, and pruning can remove cached images. The July plan acknowledges database restore requirements, but the main entry point omits them. Caddy's [Dockerfile](../../services/mushr/Dockerfile.caddy) also leaves its Cloudflare module unversioned; the local image tag alone does not reproduce identical build inputs. Jackett has `AUTO_UPDATE=true` in Compose, which deserves verification before claiming all application upgrades happen only through tag commits.

**Action:** keep the pinning policy, qualify rollback with data compatibility/backups and image availability, and distinguish version tags, immutable digests, and local builds. Say “no unpinned floating image references” rather than “nothing runs on latest”: two references correctly combine `latest` with a digest.

## Sputnik: keep the boundaries, remove the duplicate specification

The service guide and workflow note total **984 lines / 7,888 words**, plus substantial explanatory comments in Compose and the Modelfile. They repeat the read-only rationale, prompt-injection discussion, briefing publication path, mount rationale, and file allowlist.

- **The workflow introduction is obsolete.** [briefing.md](../../services/sputnik/workflows/briefing.md), lines 11–15, directs users to build manually and says the spec “cannot go stale.” A [tracked JSON export](../../services/sputnik/workflows/briefing.json) now exists and has `active: true`. Its two Code-node bodies exactly match the Markdown blocks. Make JSON the workflow definition and document credential rebinding, import/publish steps, and verification once; remove copied implementation bodies.
- **Empty-inbox behavior is not established.** The note says to enable Always Output Data on Gmail message; the export has no `alwaysOutputData` setting there or on Split Out. Calendar → Gmail list → Split Out → Gmail message → Build digest is serial. The downstream try/catch cannot ensure it runs when an earlier node emits no items. This is a code/runtime verification item, not a prose-only fix.
- **Window claims disagree.** The note says trigger and both query windows encode the same number, but mail looks back 6h and calendar looks ahead 24h. Queries have no persisted last-success cursor: “since the last check” is not accurate after outages. `maxResults=25`, no Gmail pagination, and the promotions exclusion also limit the supposedly “unfiltered” manifest. Call it a model-independent list of fetched items, not a completeness guarantee.
- **Scope the threat model to the exported workflow.** Its chain has no tool edges, fixed API requests precede inference, and the renderer uses `textContent`; those are valuable, inspectable properties. The prose generalizes them to the entire assistant, including Open WebUI and uninspected live configuration. “Nothing carries it off the host” also conflicts with intentional browser/Homepage delivery. State assumptions about credentials, configured tools, and tunnel exposure.
- **Correct measured-setting drift.** sputnik.md:263 says `num_thread 6`; the Modelfile sets 12 and includes dated benchmark results. Keep those measurements once. Thread count is not CPU affinity; there is no `cpuset` binding in Compose to substantiate the claim that choosing 12 pins execution to P-cores.
- **Replace confident diagnosis with checks.** Fabricated mail details do not prove context truncation. Verify the fetched data, truncation, prompt size, and output; do not automatically prescribe a larger context window. “Only faster memory” can improve prefill is likewise stronger than the recorded thread experiment supports.
- **Small factual cleanup:** calavera is a Surface, not a Pi; the service guide calls it one. Keep the model-independent manifest, no-tools architecture, credential backup requirement, and safe renderer explanation; cut the repeated persuasion and conversational incident retellings.

## Prevent the same drift

1. **One owner for each fact:** manifests for service membership/ports/mounts/tags; service pages for operation/recovery; host pages for hardware; agent instructions for collaboration conventions. Link instead of copying.
2. **Separate state from intent:** label plans proposed/completed/historical. Date live observations and benchmarks. A feature branch name or UI state is not evergreen setup guidance.
3. **Keep comments about reasons:** retain the explicit Wi-Fi module choice, cron PATH, n8n home mount, sibling read-only mounts and VPN/Lidarr pin constraints. Shorten duplicated narratives around them.
4. **Keep diagnoses conditional:** record symptom, evidence, mitigation, and verification. Avoid “safe,” “cannot,” “always,” or “by design” unless supported by configuration or a deliberate requirement.
5. **Fix navigation portability:** eleven concrete relative links escape the repo into sibling blog/private-memory trees. Ten work only because those sibling checkouts happen to exist here; viking's private-memory link is missing even here. Use repository-local docs or verified published links. Remove references to README sections that no longer exist (Fleet Monitoring, Pull-Based Deploys, Authenticating Private Repos).
6. **Add small checks where useful:** local link/anchor validation and a few behavior tests for health failures, supported CLI commands, and empty-inbox workflow handling. Full copied version tables are better removed than tested.
